[10] สรุปจุดเด่นทางเทคนิค (ถ้าถูกถาม)
──────────────────────────────────────────────────────────────

"เทคโนโลยีที่ใช้
  - Backend: Django 6.0.1 (Python)
  - Database: SQLite (พัฒนา) / สามารถย้ายเป็น PostgreSQL ได้
  - Static files: WhiteNoise (serve ไฟล์โดยไม่ต้อง web server แยก)
  - Payment: Opn / Omise — PromptPay QR + Webhook อัตโนมัติ
  - Frontend: Vanilla HTML/CSS/JS ไม่พึ่ง framework เพื่อให้โหลดเร็ว
  - UI: ทำงานได้ดีทั้ง Desktop

ความปลอดภัย
  - ทุก endpoint ที่เกี่ยวกับเงิน validate ฝั่ง server เท่านั้น
  - ไม่เชื่อค่าจาก frontend ที่ส่งมา
  - Django CSRF protection ครบทุกฟอร์ม
  - Coins คำนวณจากยอดจริงในฐานข้อมูล ไม่ใช่จาก input ผู้ใช้

Scalability
  - แยก static files ออกจาก application server แล้ว
  - Database query ใช้ select_for_update() ในการหักสต๊อก
    เพื่อป้องกัน race condition กรณีสั่งพร้อมกัน"


──────────────────────────────────────────────────────────────
[11] Q&A — คำถามที่อาจโดนถาม
──────────────────────────────────────────────────────────────

Q: ถ้าลูกค้าไม่มา QR หมดเวลาแล้วจะเป็นยังไง?
A: ระบบเปลี่ยนสถานะ order เป็น 'หมดอายุ' อัตโนมัติ
   สินค้าไม่ถูกตัดสต๊อก ลูกค้าสั่งใหม่ได้เลย

Q: ถ้า payment gateway ล่มจะเป็นยังไง?
A: หน้าเว็บแจ้ง error ให้ลูกค้าทราบทันที ไม่ค้างหน้า
   Staff สามารถ mark order ว่าชำระแล้วด้วยตัวเองได้ (offline mode)

Q: ระบบ Coins ปลอมแปลงได้ไหม?
A: ไม่ได้ เพราะ Coins คำนวณจากยอด order จริงในฐานข้อมูล
   ฝั่ง frontend ส่งค่ามาไม่ได้ ต้อง validate ผ่าน server ทุกครั้ง

Q: ลูกค้าไม่ login ก็ซื้อของได้ไหม?
A: ได้ — ระบบใช้ session สำหรับลูกค้าที่ไม่ได้ login
   ประวัติออเดอร์จะถูก link กับ account ถ้า login ในภายหลัง

Q: สต๊อกจะติดลบได้ไหมถ้ามีคนสั่งพร้อมกัน?
A: ไม่ได้ เพราะใช้ select_for_update() lock ระหว่างหักสต๊อก
   และมีการ max(0, stock - qty) กันสต๊อกติดลบไว้อีกชั้น

Q: แปลงผักถ้ามีคนจองทับกันจะเป็นยังไง?
A: ปฏิทินในหน้าแปลงแสดงวันที่ถูกจองไว้แล้ว (สีแดง)
   ลูกค้าเลือกวันที่ว่างได้เลยก่อนจอง

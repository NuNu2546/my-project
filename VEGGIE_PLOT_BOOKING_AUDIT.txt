หัวข้อ 1: Models — ตาราง/โมเดลที่เกี่ยวกับแปลงผักและการจอง
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

สถานะ: ❌ ไม่มี Model ใดๆ ที่เกี่ยวกับแปลงผักหรือการจองอยู่ในระบบเลย

store/models.py มี Model เพียง 4 ตัว ทั้งหมดเกี่ยวกับการซื้อสินค้า:
  - Product      : สินค้าใน Shop
  - Order        : คำสั่งซื้อ (สถานะ, ชื่อลูกค้า, เบอร์, ที่อยู่, ยอดรวม, charge_id ฯลฯ)
  - OrderItem    : รายการสินค้าในออเดอร์
  - OrderStatusHistory : ประวัติการเปลี่ยนสถานะออเดอร์

ไม่มี:
  - Plot model (แปลงผัก)
  - Booking model (การจอง)
  - ตารางใดๆ ในฐานข้อมูลที่เก็บข้อมูลแปลงหรือการจอง

โค้ดทั้งท่อน (copy จาก views.py บรรทัด 536-558):
---
def process_booking(request):
    if request.method == 'POST':
        # 1. รับค่าที่ส่งมาจาก Hidden Input
        plant_name = request.POST.get('selected_plant')
        start_date_str = request.POST.get('start_date') # จะได้เป็นข้อความเช่น '2026-03-18'

        if plant_name and start_date_str:
            start_date = datetime.strptime(start_date_str, '%Y-%m-%d').date()

            days_needed = PLANT_GROW_TIMES.get(plant_name, 0)
            price_per_day = 5
            total_price = days_needed * price_per_day

            harvest_date = start_date + timedelta(days=days_needed)

            return render(request, 'booking_success.html', {
                'plant': plant_name,
                'start_date': start_date,
                'harvest_date': harvest_date,
                'price': total_price
            })

    return redirect('plot_detail')
---

ระบบที่มีอยู่แล้ว:
  ✅ Order + OrderItem       : คำสั่งซื้อสินค้า
  ✅ OrderStatusHistory      : ประวัติสถานะ (auto-track ผ่าน save() override)
  ✅ Opn Payments PromptPay  : QR Payment, Webhook
  ✅ session['my_orders']    : จำออเดอร์ไว้ 1 ปีในเบราว์เซอร์
  ✅ /my-orders/             : หน้าดูประวัติการซื้อ
  ✅ /order/<id>/track/      : ติดตามสถานะ

ประเมินการนำระบบมาใช้ซ้ำกับ Booking:

ตัวเลือก A: ใช้ Order model ร่วมกัน (reuse)
  แนวคิด: สร้าง "booking order" เป็น Order ปกติ แต่มี type='booking'
           ใส่ข้อมูลแปลงลง OrderItem (product_name = "แปลง A12 - มะเขือเทศ")
  ข้อดี:
    - จ่าย PromptPay QR ได้ทันทีโดยไม่ต้องแก้ Omise code เลย
    - เข้าระบบ my-orders ได้เลย (ลูกค้าเห็นทั้งสินค้าและการจองในที่เดียว)
    - OrderStatusHistory รองรับ status tracking แปลงได้
    - STATUS_CHOICES ที่มีอยู่ใช้ได้เลย (pending → paid → ...)
  ข้อเสีย:
    - ต้องแยก type ออกมาให้ชัด (shop order vs booking order)
    - ไม่มีฟิลด์: plot_id, start_date, harvest_date, plant_name แบบ typed
    - ต้อง encode ข้อมูล booking ลงใน JSON field หรือ OrderItem (ซับซ้อนขึ้น)
    - ไม่สามารถ query "แปลง A12 ถูกจองช่วงไหนบ้าง" ได้โดยตรง

ตัวเลือก B: สร้าง Booking model แยก
  แนวคิด: สร้าง model ใหม่ PlotBooking เก็บ plot_id, plant, start_date,
           harvest_date, status, charge_id (เชื่อม Opn Payment)
           แล้วเชื่อม my-orders ให้แสดงทั้ง Order และ PlotBooking
  ข้อดี:
    - ข้อมูลครบถ้วน query ง่าย ถูกต้องตามหลัก OOP
    - ตรวจสอบ date overlap ได้สะดวก
    - รองรับ feature ในอนาคตได้ง่ายกว่า (เช่น renewal, แสดง plot calendar)
  ข้อเสีย:
    - ต้องแก้ Payment flow ให้รองรับ PlotBooking.charge_id ด้วย
    - ต้อง integrate my-orders ให้ดึงทั้ง Order และ PlotBooking
    - code เยอะขึ้น

คำแนะนำ: ตัวเลือก B (แยก model) เหมาะกว่าในระยะยาว
  เหตุผล: business logic การจองแปลง (ช่วงวัน, ความขัดแย้ง, รายแปลง)
           แตกต่างจาก product order มากพอที่จะ justify model แยก

การเชื่อม Opn PromptPay:

การตัดสินใจสำคัญ 5 ข้อ:

  [D1] Model: ใช้ Order model ร่วม หรือสร้าง PlotBooking model แยก?

       → ถ้า ฿/วัน: ยืนยันว่า ฿5/วัน ถูกต้องหรือต้องต่างตามแปลง?
       → ถ้า ฿/เดือน: ต้องคำนวณจำนวนเดือนจาก start_date ถึง harvest_date

  [D3] แปลง: จะ hardcode 6 แปลงไว้ใน code หรือให้ Admin จัดการผ่าน Admin panel?
       → ถ้า hardcode: ไม่ต้องสร้าง Plot model แยก แต่เพิ่มแปลงต้องแก้ code
       → ถ้า DB: ต้องสร้าง Plot model + admin

  [D4] ลูกค้า: ต้องกรอกชื่อ/เบอร์ตอนจองหรือดึงจาก session ของระบบ login ในอนาคต?
       → ตอนนี้ไม่มี login ระบบ → ต้องให้กรอกตอนจองก่อน

  [D5] ชำระเงิน: บังคับจ่ายก่อนยืนยันการจอง หรือจองก่อนแล้วค่อยจ่าย?

       → ถ้าจองก่อนจ่ายทีหลัง: ต้องมี status "รอชำระ" และ reminder
